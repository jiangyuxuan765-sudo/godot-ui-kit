# 硬约束清单

`theme/规范.md` 的可执行摘要。规范是叙事体（877 行，按「第几套踩了什么坑」组织），
适合回溯某次问题的来龙去脉，不适合动手前逐条核对。这份按**阶段**收口，每条注明
谁来查。

三种标记：
- **[自动]** —— 有断言，跑 `bash tools/验收/全量验收.sh <套>` 就查了，不用肉眼看
- **[半自动]** —— 脚本能报可疑项，但真假要人判（如 HBox 拉伸的告警）
- **[人工]** —— 判不了，只能看图或看代码（如「字色落在这张贴图上是否可见」）

不要把 [人工] 条目改写成 [自动] 断言凑数。判不了就是判不了，假装能判比不查更糟：
色相占优那条断言至今是红灯，价值恰恰在于它没被调松。

## 阶段 0 立项（参考图/提示词 → 风格卡）

- [人工] **七类骨架必须与最近两套都不同**。七类 = 按钮、进度、滚动条、滑块、
  物品框、导航、面板。规范 5.25/5.26/5.27 各有一张「骨架对照表」，新套开工前
  先对着看，避免出现「换了配色的同一套」。
- [人工] **确定底色明暗**。亮底套（如拓荒纪事旧纸 `#E8DCC4`）和暗底套的字色、
  提亮值、背景判定全都不同，定错了后面每一层都要返工（见规范 5.23/5.27）。
- [自动] 在 `tools/验收/套别配置.py` 登记新套：素材目录、主题文件、场景文件、
  底色、暖色占优、亮底。**不登记后面三层脚本全部跑不起来**。

## 阶段 1 出素材（生成脚本 → SVG）

- [自动] **零位图**。不得出现 `<image>` 或 `data:image`。
- [自动] **SVG 的 width/height 必须等于 viewBox**。不一致等于整张图被缩放，
  边框粗细会变。
- [自动] **尺寸逐张对账契约**。
- [自动] **文件名与契约完全对应**，无缺无多。
- [人工] **确定性**：脚本必须可字节级复现（伪随机走 LCG，不用 `random`）。
  验证法：备份素材目录 → 重跑生成脚本 → `md5` 逐张比对。
- [人工] **图标要撑满画框**。56×56 的框里只占 34px 会显得细小（规范 5.25）。

### 尺寸契约怎么定（最容易错的一步）

**九图保护只对 `NinePatchRect` 和 `StyleBoxTexture` 有效，`TextureRect` 没有。**
`TextureRect` 直接把贴图拉到控件尺寸，所以：

- 走 `TextureRect` 的素材 → 尺寸**必须等于场景里控件的实际尺寸**，差一像素就是
  非等比拉伸（卡牌框 180×228 塞进 160×196 的框，切角被拉歪，探针查出来的）
- 走 `NinePatchRect` / `StyleBoxTexture` 的 → 允许拉伸，但要守住下面那条 margin

契约不是「照抄派生源」。派生源的场景尺寸可能和本套不一样，照抄就会变形。

## 阶段 2 装 theme（派生 → import）

- [自动] **`texture_margin` 的 T+B 必须 < 贴图高、L+R < 贴图宽**。相等或超出，
  中心行/列就是 0 或负，九图完全退化，控件一拉就整张图被当边框拉长。
  历史上一次栽 4 处（进度条空槽/填充 T+B 正好等于图高）。
- [自动] **滑块／滚动条／分隔线的 `content_margin` 短轴必须显式写**，否则控件
  画不出来。`StyleBoxTexture` 的 `content_margin` 缺省（`-1`）时**逐边回退到
  `texture_margin`**；这几张图只沿长轴做九宫格，短轴 `texture_margin` 天然是 0，
  于是 `get_minimum_size()` 短轴 = 0 —— 而 `HSlider`/`ScrollBar`/`Separator`
  正是拿这个值当**轨道（控件）厚度**。
  - 滑块：槽和填充条 0 像素高，只剩走 `icons/grabber` 的拖动键（Texture2D 不经
    stylebox），屏幕上是一个悬空小键。**这就是用户看「战术锋线」第一眼说的
    「为什么没有拖拽条，只有按钮」** —— 五层+四层全绿，人眼一眼看出。
  - 分隔线更彻底：整个控件厚度就是它，实测画 **0/420 列**，一个像素都没有。
    `VSeparator` 反而没事，它的厚度轴是横轴，`left/right` 有值。
  - 短轴取贴图短边全值即可；`content_margin` 只影响最小尺寸与内容区，不改绘制
    矩形，补它不会挪动外观。
  - ★**判据只覆盖轨道类和分隔线，不能推广到「所有 min 短轴为 0 的 stylebox」**。
    实测反证：第一套 ProgressBar 的 `fill.min=(32,0)`、第六套 HSlider 的
    `grabber_area.min=(16,0)`，渲染出来都是满格 —— ProgressBar 填充高另有来源。
    一刀切会每套报一堆假警，把真问题淹掉。见 `检查主题.py` [8] 的 `厚度项` 表。
  - 补上这条判据后扫出**十一/十二/十三/十四套的分隔线全有同一缺陷**（都已修）。
    四层验收此前查不到：几何层量的是控件矩形（滑块 406×52 是对的），截图层判
    非背景像素（面板底本来就亮），谁都碰不到「厚度」这个量。
- [自动] **`ext_resource` 必须全部排在 `sub_resource` 之前**。插到后面 `.tscn`
  直接解析失败（`Unknown tag 'ext_resource'`）。
- [自动] **自身 uid 必须合法且全库唯一**。uid 是 Godot 的 base-N 编码，只含小写
  字母数字；手搓的串会被判 invalid UID，静默回退到文本路径并报 WARNING。
  正确做法：`ResourceUID.create_id()` 生成（见 `tools/验收/_orig_genuid.gd`）。
- [自动] **交叉引用 uid 与目标文件实际 uid 必须一致**。`ext_resource` 同时写
  uid 和 path，uid 失效时 Godot **静默回退到 path 照常加载，不报错也不告警**，
  所以断链能长期潜伏。皇室战争和星舰指令的场景都引用着已不存在的手搓 uid
  （`uid://cr11royaletheme`、`uid://cr12starcmdtheme`），直到加了这条才查出来。
  只查「自身 uid」查不出这类问题。
- [自动] **贴图引用全部指向本套目录且文件存在**。派生残留会让整套指向上一套。
- [半自动] **素材着落**：每张 SVG 都应被 theme 或场景引用。有意备用的图允许存在，
  但历史上多次是「出了图忘了接」。
- [人工] **改完必须跑 `--import`**，否则 uid 不进 `.godot/uid_cache.bin`，加载报
  WARNING。import 前后用 `md5 -q` 记基线查 churn。
- [人工] **Godot 编辑器开着时不要改 `.tscn`**，会被整文件 resave 污染，提交前查
  diff 行数。
- [人工] **派生时颜色替换要按文件里的实际精度**。场景里是 `Color(0.043, 0.129,
  0.235, 1)` 三位小数，用六位 `0.043137` 去匹配会**静默失败**，背景一直是上一套
  的颜色。改完采样渲染图角点像素确认，别只看替换脚本报了成功。
- [人工] **场景背景 `ColorRect` 的 color 不在 theme 里**，派生时最容易漏。
- [人工] **亮底套不能照抄暗底套的字色**。按具名 key 逐项改墨色（拓荒纪事改了
  11 项），不要全局替换色值——同一个骨白在深色按钮上是对的。
- [人工] **亮底套要把 `modulate_color` 的提亮值压回 1**。源套用 1.12~1.2 给暗
  贴图提亮，本套贴图本身就亮，照搬会过曝发白。

## 阶段 3 测试台验收

- [自动] **控件实测尺寸对账**（探针）。`TextureRect` 横纵缩放比必须相等；
  `TextureProgressBar` 没开 `nine_patch_stretch` 就不该被拉伸。
- [自动] **内容宽度不超视口**。`Inner.get_combined_minimum_size().x` 要 ≤
  视口宽 − Margin 左右。Label 默认不换行，超长标题会把 VBox 最小宽撑爆
  （曾撑到 994 > 竖屏 804，右侧内容全被裁）→ 加 `autowrap_mode = 2`。
- [半自动] **HBoxContainer 会把子节点纵向拉到最高兄弟的高度**。第十二、十三、
  十四套都栽过。判定基准必须是 `get_combined_minimum_size().y`，**不是**
  `custom_minimum_size.y`——Button 的自然高还含字体行高和 content_margin
  （cms 写 82，组合最小其实 86），拿 cms 当基准会把整排没被拉伸的按钮全报一遍。
  修法：给该节点 `size_flags_vertical = 4`（SHRINK_CENTER）。
- [自动] **逐屏非背景占比在 4%~92% 之间**。低于 4% 是空屏/控件没渲染出来，
  高于 92% 是被某面板铺满（拉伸失控）。
- [半自动] **色相构成符合本套定位**（腐蚀 K=4 后统计结构性色块）。腐蚀是必须的：
  每个组件都有 1.5–3px 描边和辉光轮廓，边缘像素远多于填充面积，直接逐像素统计
  会被描边色压偏。
- [人工] **排除 `@` 开头的节点**。那是引擎给 `ScrollContainer`/`PopupMenu` 自动
  生成的内部滚动条，贴图为空、尺寸被拉到 512/3000。初版探针把它们算进去，报了
  6 个假变形。
- [人工] **交互只在运行时生效**。编辑器里拖不动是正常的，必须运行场景
  （Mac ⌘R，不是 F6）。

### 截图这一步的两个硬坑

- **不能加 `--headless`**。它会强制 dummy 驱动盖掉 `--rendering-driver opengl3`，
  `get_texture().get_image()` 拿到空纹理，存出来是纯色图，而验收还会「通过」。
  报错特征：`rendering/dummy/storage` + 窗口高变成 64。
- **窗口高必须 ≥ ScrollContainer 视口高**。`scroll_vertical` 上限是
  内容高 − 视口高，画面只能看到窗口高那一截。旧的 900 高窗口配 1500 视口，
  底部 600px **永远截不到且不报错**——四套的验收都漏了尾部。
  现在 `截图.gd` 会直接拒绝跑并提示。
- **截图按套分目录**存放（`tools/验收/截图/<套别>/`）。共用一个目录时，
  `SKIP_SHOT=1` 会静默拿到上一套的图再用本套底色判——皇室战争的深蓝底配星舰
  指令的靛蓝底，占比报 100%，而这种荒谬数字仍然「有结论」，比报错更难发现。

### 占比不达标时，先分清「风格稀疏」和「画了但看不见」（第十六套线框仪表）

纯线框套（零实填）天生贴近 4% 下限。第十六套第一版报 2.71%–3.80%，看着像
「判据对线框风格太严」，其实是真故障：量对比度发现 76%–95% 的非背景像素低于
1.5:1 —— **线框风格允许稀疏，但每根画出来的线都必须够亮**（WCAG 非文本 3:1）。
病灶是 `LINE #0A6E70 @0.55 = 1.73:1`、`LINE2 #0E3A3C @0.10 = 1.03:1`。
**修法是提亮，不是放宽下限。**

三条连带教训，每条都真的让我改错过一次：

- **色值和透明度是乘在一起的，只改一个等于没改。** 第一次修只把色值换亮
  （`#1FA8AA`/`#12666A`），占比几乎没动 —— 斜纹仍压在 `@0.10`，换了亮色还是
  1.1:1。必须两处一起定。
- **拿"低对比像素占多数"当缺陷判据之前，先用已交付套跑同一把尺子。** 修完仍报
  77%–95% 低于 1.5:1，看着像没修好；拿**用户已验收的战术锋线**跑同一脚本是
  56%–82%，同一区间 —— 那个数大半是辉光和抗锯齿的过渡像素，任何带发光的套都这样。
- ★**自己另写的分析器和闸门必须用同一个背景口径，否则会照着不存在的故障改素材。**
  我的脚本把「非纯黑」全算内容，于是面板极暗底 `PANEL #050A0C`（渲染成
  `rgb(5,10,12)`，1.06:1）被算成"看不见的内容"，一屏冲到 95.1%；而
  `图像.背景判定器` 按「够暗且够中性」本就把它判成**背景**。换用闸门自己的判定器
  重量：线框仪表 22.9%–57.5% 达 3:1，**优于**战术锋线的 14.7%–53.1%。
  质疑闸门结论前先对齐口径，别急着改素材。

### 底色不要手写

`套别配置.py` 里 `"底色": None`，由 `取()` 从场景根 `ColorRect` 读真值。手抄两次
两次错：拓荒纪事按风格名「旧纸」填 (232,220,196)，实际是深棕皮革 (103,81,60)；
皇室战争填紫黑 (26,20,46)，实际是深蓝 (11,33,60)。两次都导致背景判不出来、
占比冲到 93%+ 并误报「拉伸失控」。

背景判定的色偏容差也必须由底色自身推导，不能硬编码。原先写死 12（义体裂界
#07070B 的 max−min=4 得来），碰上星舰指令靛蓝底 rgb(7,13,21) 就崩了：它自身
max−min=14 > 12，**底色自己都不被判成背景**，75% 的纯底色像素全算成内容。

## 阶段 4 注入游戏

**已实测跑通三次**：
- 2026-08-26 第十四套-义体裂界 → `卡牌对战`（那次的坑：26 处 inline StyleBox
  要先清、主题缺 8 个游戏要的类型、**汉字 tofu**——四层全绿而界面四个方框，
  字形层就是那次加的）。
- 2026-08-31 第十五套-战术锋线 → `战术交火`（Godot 4.7，本节按这次的顺序写）。
- 2026-09-01 第十六套-线框仪表 → `战术交火-线框HUD`（= `战术交火-换肤前备份`
  的副本，用户要求"给这个备份再换一次 UI"）。**灰默认皮 → 纯黑线框皮，是本系列
  第一次跨到纯黑底**，所以这次补了第六层「对比度层」，测试从五层扩到六层。

三次的共同点：**主题一定缺游戏要的类型**，注入前必须对类型表。
不同点：卡牌对战 有 26 处 inline override 要清，两次战术交火 都是 0 处，
所以后两次能直接验证「纯 theme 换肤」这条路本身。

**第三次新抓到的（都不是设想）**：

- ★★ **旧断言的错前提会被副本带回来。** 副本是从 `-换肤前备份` 拷的，而那份
  备份里的 `测试字形.gd` 用的是**已被证伪**的判据（「有 gui/theme/custom 就断言
  主题.default_font != null」）。第十五套那轮已经查明 Godot 字体是**分层兜底**的
  ——主题没写 `default_font` 时 `gui/theme/custom_font` 仍生效——并在
  `战术交火` 里换成了查 `ThemeDB.get_fallback_font()` 能否画汉字（更严）。
  但那次的修正只落在**已交付项目**里，备份没跟着改，于是这次注入后字形层当场
  报红。**修法是把修正版移植过来，不是把主题塞个 default_font 去迎合错断言。**
  教训：修断言时要问「这条断言在几份拷贝里」，备份和 worktree 都是拷贝。
- ★ **`cp -R <套目录> <项目>/UI/` 在 `UI/` 不存在时会把套目录变成 `UI/` 本身。**
  备份项目根本没有 `UI/` 目录（换肤前不需要），于是 81 张 SVG 直接散落在
  `UI/` 下，而 theme 引用的是 `res://UI/线框仪表/...` —— 全部断链。第二次 `cp`
  才建出正确的 `UI/线框仪表/`，结果两处并存、81 张重复。
  **先 `mkdir -p UI` 再拷，拷完 `ls` 一眼确认层级。**
- ★ **注入后第一遍 `--import` 报一片 `Unable to open file: ...ctex` 是加载顺序，
  不是错误。** theme 比它引用的贴图先被导入，此刻 ctex 还没生成。第二遍 0 报错。
  **判据不是"import 有没有报错"，而是逐个查 `StyleBoxTexture.texture != null`**
  （本次 76/76 有图、29/29 图标非空）。
- ★ **探针实例化场景前必须 `await process_frame`**，否则 autoload 还没注册完，
  场景脚本里的单例引用报 `Identifier not found`，**而探针照样跑完报"全部通过"**
  ——场景是加载了、只是脚本没挂上，文字段数照样够。假绿。字形层开头本就有这句，
  我新写对比度层时漏了，靠对比 stderr 才发现。

下面标「★」的是踩过的坑，不是设想。

**1. 体检**（`tools/脚手架/扫描游戏.py --项目 <路径>`）

- **换肤失效的头号原因是 inline StyleBox override**。节点上的 override 会盖掉
  theme，扫游戏所有 `.tscn` 先列出来。战术交火 报 0 处，注入才这么顺；
  卡牌对战 报 26 处 + 代码里 11 处，那种要先清。
- 顺带确认 `[3] theme 引用点`：报「无」说明还没接过 theme，是干净的起点。
- **每个 `TextureRect`/`NinePatchRect` 的实际尺寸要与本套 81 张素材的契约对表**，
  对不上的要么重出图要么改游戏节点（九图保护只对 NinePatchRect 和
  StyleBoxTexture 生效，TextureRect 是整张缩放，必须尺寸吻合）。
  战术交火 一个都没有（全走 Button/PanelContainer/ProgressBar/HSlider），
  这条没被实测检验过，别当成「已验证」。

**2. 备份**

游戏项目不一定是 git 仓库（战术交火 就不是），`cp -R` 一份 `-换肤前备份`。
这份备份不只是回滚用的——第 5 步的差分对照要拿它出图。

**3. 注入**

- `.svg` 和 `.svg.import` **一起拷**。`.import` 里的 dest_files 按 res:// 路径
  算 md5，目标项目里路径一样，uid 就能对上；只拷 .svg 会重新导入换一批 uid，
  theme 里几十条引用全部落空。
- `project.godot` 里写 `gui/theme/custom`。
- ★**注释符只能是 `;`。** 写成 `#` 时 `gui/theme/custom` 读出来是空字符串，
  **不报任何错**：`ThemeDB.get_project_theme()` 返回 null，界面照旧默认灰皮，
  看起来就像「配了但没生效」。第一次注入在这里栽过。
- 验收方式：跑一个脚本遍历 theme 的所有 stylebox/icon，确认没有 null、
  没有 texture 落空（战术锋线 是 104 处全部可解析）。
- ★**先对一遍「游戏用到的控件类型」和「theme 覆盖的类型」。** 测试台只摆
  TextureRect 看图，不代表 theme 里有对应条目：战术锋线 的滑块/滚动条七张
  SVG 在测试台里只是摆着，theme 里一个条目都没有，而游戏用了 2 个 HSlider
  + 1 个 ScrollContainer——直接注入的话这两处保持 Godot 默认灰皮，
  偏偏是界面上最扎眼的地方，四层验收也查不出来（素材着落那条只要求
  「被 theme 或场景用到」，摆在场景里就算用到了）。
  注入前用 `grep -o 'type="[A-Za-z]*"' 游戏/*.tscn | sort -u` 对一遍。
  补条目时 `icons/grabber*` 三项都要写，缺 grabber_disabled 会回退成默认灰圆点。

**4. 实测：跑游戏自己的测试**

这一步的价值在于抓「换肤引起的功能/排版回归」。战术交火 抓到两处真回归：

- ★**几何层：窄框被 content_margin 吃穿。** 本套 PanelContainer 的
  content margin 是 40/32/40/32，撑在测试台 460 宽的框上很稳，套到 HUD 里
  192 宽的战报框上横向被吃掉 80，内容只剩 112，16px 中文一行折成两三行，
  7 行战报内容高冲到 238 而框只有 132，文字从中间被裁断。
  **解法是加 type variation（`PanelContainerHUD`，边距 20/10/14/14），
  不是改游戏的布局偏移**——改偏移会连带动到截图层的取样框。
  窄框的判断标准：框宽 < content_margin 左右之和的 3 倍就要单独给变体。
- ★**字形层：断言的前提本身是错的。** 原断言是「有 gui/theme/custom 就要求
  主题的 default_font != null」，理由记着「主题会盖掉 custom_font」。注入后
  当场报错，而同一次运行里 37 段文字的逐字形检查全过——**Godot 的字体是分层
  兜底的**，主题没写 default_font 时 `gui/theme/custom_font` 仍然生效
  （实测 `ThemeDB.get_fallback_font()` 和 `Label.get_theme_default_font()`
  都是黑体，八个汉字零外来字形）。「盖掉」只在主题**确实写了**时才发生。
  判据改成查 `ThemeDB.get_fallback_font()` 本身能不能画汉字——**这比原来严**，
  原来只看字段非 null，一个只含拉丁字形的字体照样过。
  改完反向验证：注释掉 custom_font，新断言当场报错且与 31 段 tofu 报告同时
  触发，三条独立证据同指一个根因。

**5. 差分对照：证明皮真的换上了**

五层全绿只证明「功能没坏」，**不证明「皮换上了」**——theme 没接上时五层
照样全绿。拿备份的截图和新截图逐张相减：

- 有 UI 的每张都要大幅改变（战术锋线：全图 8%–63%，面板区 36%–99%）。
- **必须有一张纯 3D 无 UI 的反向对照**（战术交火 的 `7_无HUD对照`）。
  它应当接近 0%（实测 0.00%）；若它也大变，说明差异来自渲染抖动而非换肤，
  其余数字全部不可信。

**6. 对比度**

★**取样框必须来自布局探针读的 `global_position`/`size`，不能照着截图目测。**
目测框把「按钮字」框到 y=1330..1400，而按钮真实在 1404..1466，量到的「最亮
像素」是面板绯红描边而不是白字，算出 4.15:1 误报「对比度不足」。
★**但探针坐标也不能盲信**：探针实例化场景时不会跑「代码建的节点」
（战术交火 的枪格排是 `_建枪格()` 建的），那一段缺席会让后续 y 坐标整体上移。
主界面这类有代码建节点的场景，坐标要从**截图自身的行/列剖面**反推。
取样时取「最亮半个百分位」当字色、「暗十分位」当底色——直接取平均会把字和底
混成中灰，比值虚高。战术锋线 17 个区块实测 6.22:1 ~ 18.45:1，全部过 AA。

★★**上面这套像素法只是权宜，跨明暗换皮时要改成 Godot 侧直查（第六层）。**
2026-09-01 灰默认皮 → 纯黑线框皮那次补了 `tests/测试对比度.gd`（照抄
`荒野生存/tests/测试对比度.gd`）：`get_theme_color` 拿控件**实际解析到的**字色
（变体覆盖也算进去），底色取最近祖先面板 StyleBox 贴图的**中心像素**乘
`modulate_color`。像素法的病根是描边像素比字芯多，会把描边当底色 —— 荒野生存
那轮量出 9.71:1 而真实是 1.29:1。Godot 侧查没有这个歧义。

这一层还有两条本次实测出来的要点：

- ★**FPS 的裸 HUD 文字"底色不可判"，必须单列交人眼，不能编一个底色糊过去。**
  战场没有页面底 `ColorRect`，血甲标/弹药/提示条直接叠在渲染出来的 3D 地图上，
  那个底是逐像素变化的画面。本次 41 段里 13 段落在这一类，探针把它们打印成
  「转人眼」清单，**既不计入通过也不伪造断言** —— 有面板包着的 28 段才自动判。
  假装能判比不查更糟。
- **BBCode 的 `[color=#xxxxxx]` 取不到，要单独对表。** 本次 4 支语义色
  （按键高亮/部位金/击倒红/匣空灰）对纯黑面板底实测 5.61:1 ~ 11.13:1。
- 阈值 4.5:1（大字 3:1）是 WCAG AA 的外部标准，**不存在调松让它变绿的空间**。
  写完先手动把字色改成贴近底色，确认它真报红（本次改坏后 10 段报红、退出码 1）。

换肤前后**节点树与功能必须不变**：两次战术交火 都只多了一行
`theme_type_variation`（战报框加 `PanelContainerHUD` 窄框变体，否则 7 行战报被
默认 content_margin 挤成 13 行、高 238 > 框 132）。
