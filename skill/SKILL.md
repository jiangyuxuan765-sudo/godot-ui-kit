# Godot UI 换肤流程

从参考图/提示词到游戏里换肤，五个阶段。**每个阶段有闸门，闸门不过不许进下一阶段** ——
四套主题的经验是每层都会出错，且错了不当场发现就会带到下一层，回溯成本翻几倍。

## 环境设置（先读这段，否则命令全跑不通）

这套流程的命令不在 skill 自己的目录里跑，要在一个**装了脚本和素材的 Godot 项目目录**里跑。
下文一律把这个目录记作 **`<套件库>`**。它可以是：

- **作者本机的完整库**（含全部历史套别）；或
- **随 skill 一起分发的最小可运行包**（如 `godot-ui-kit`，含验收脚本 + 一个完整演示套）。

两种都满足同一个布局，相对路径都从这里起：

```
<套件库>/
  project.godot            Godot 项目壳（验收要在这里跑）
  tools/脚手架/            新建套别.py / 派生主题.py / 扫描游戏.py / 生成uid.gd
  tools/验收/              全量验收.sh / 检查素材.py / 检查主题.py / 检查截图.py /
                           探针.gd / 截图.gd / 套别配置.py / 图像.py / 硬约束清单.md
  theme/                   各套 .tres + 规范.md
  scenes/                  各套 theme测试-<套名>.tscn 测试场景
  UI/<套名>/               各套的 .svg + .svg.import
```

**动手前先 cd 到 `<套件库>`，并确认两件事：**

1. `python3` 可用。验收脚本只用 Python 标准库，**不需要 pip 装任何东西**。
2. 找到本机 Godot 4 可执行文件，设进环境变量 `GODOT`：
   - macOS：`export GODOT="/Applications/Godot.app/Contents/MacOS/Godot"`
   - Windows：`set GODOT=C:\path\to\Godot.exe`（或 `$env:GODOT=...`）
   - Linux：`export GODOT=/usr/local/bin/godot`
   不设的话脚本按 macOS 默认路径找，找不到会提示你用 `GODOT=` 覆盖。

**能力前提**：阶段 3 的截图层和阶段 4 的「逐张看图」要求这个环境**能开真窗口、能读图**
（纯无头/无视觉环境跑不了截图校验，会卡在那一层）。跑通冒烟测试即代表环境齐了。

先读这两份，别凭记忆做：
- `<套件库>/tools/验收/硬约束清单.md` —— 按阶段收口的可执行摘要，每条标了 [自动]/[半自动]/[人工]
- `<套件库>/theme/规范.md` —— 叙事体，按「第几套踩了什么坑」组织，回溯具体问题时查

## 阶段 0 立项 → 风格卡

产出一张风格卡（写在对话里，不用建文件），包含：套别名、序号、七类骨架、配色 token、
底色明暗。

**七类骨架必须与最近两套都不同。** 七类 = 按钮、进度、滚动条、滑块、物品框、导航、面板。
规范 5.25/5.26/5.27 各有一张骨架对照表，开工前对着看，避免做出「换了配色的同一套」。
已用过的骨架：

| 套 | 面板 | 按钮 | 进度 |
|---|---|---|---|
| 十一 皇室战争 | 圆角厚板 | 圆角胶囊 + 底唇 | 圆头槽 |
| 十二 星舰指令 | 切角装甲板 | 切角板 + 铆钉 | 刻度导轨 |
| 十三 拓荒纪事 | 皮革订本 | 皮革压印 | 正字刻痕 |
| 十四 义体裂界 | 斜切数据舱 | 右倾平行四边形 | 梯形分段块 |

**底色明暗定错后面每层都要返工。** 亮底套（组件贴图是浅色）的字色、`modulate_color`
提亮值、背景判定全都不同。注意「亮底」指组件贴图，与场景底色是两件事——拓荒纪事叫
「亮底旧纸风」，场景底其实是深棕皮革 `rgb(103,81,60)`。

有参考图就先看图，把配色 token 从图里取样，不要凭风格名想象。

**闸门**：登记进 `套别配置.py`。不登记后面三层脚本全部跑不起来。

```bash
python3 tools/脚手架/新建套别.py --套 <套别名> --序号 第N套 --暖色占优 <是|否|未定>
# 亮底套加 --亮底
```

它会查名字/序号冲突、建素材目录、生成两个全库未占用的 uid（**记下来，阶段 2 要用**）。
风格没定死时 `--暖色占优 未定` 写 None（不做该断言），别为了让验收全绿填假值。

## 阶段 1 出素材 → 81 张 SVG

写 `tools/生成<套别名>素材.py`。**照抄一份最近的生成脚本改，不要从零写** ——
`生成义体裂界素材.py`（1123 行）是最完整的一份，公共骨架都在里面：

- `w(name, body, wd, ht, defs)` 落盘一张 SVG
- `vgrad/hgrad` 渐变、`cham/para/hexa` 形状、`P/R/L/C` 图元包装
- `sz(name, fallback)` 从尺寸契约读尺寸（**新套没契约时走 fallback**）

文件名必须与派生源逐一对应（81 张），否则阶段 2 没法按名替换 `ext_resource`。

三条硬约束：
- **零位图**：不许有 `<image>` 或 `data:image`
- **width/height 必须等于 viewBox**：不等于整张图被缩放，边框粗细全变
- **确定性**：伪随机走 LCG，不要用 `random`。验证法是备份目录 → 重跑 → `md5` 逐张比

**尺寸契约是这一步最容易错的地方。** 九图保护（`texture_margin`）只对 `NinePatchRect`
和 `StyleBoxTexture` 有效，`TextureRect` **没有** ——它直接把贴图拉到控件尺寸。所以：

- 走 `TextureRect` 的素材 → 尺寸必须**等于场景里控件的实际尺寸**
- 走九图的 → 允许拉伸，但要守住 `texture_margin` 那条（阶段 2）

契约不是照抄派生源。卡牌框 180×228 塞进 160×196 的框，缩放 0.889 vs 0.860 不等比，
切角被拉歪——这个错从星舰指令继承了两套才被探针查出来。

**闸门**：
```bash
python3 tools/验收/检查素材.py --套 <套别名> --写契约   # 首次建契约
python3 tools/验收/检查素材.py --套 <套别名>            # 之后每次改素材都跑
```

## 阶段 2 派生 theme 与测试场景

```bash
python3 tools/脚手架/派生主题.py --源 <源套> --目标 <新套> \
    --主题uid <阶段0给的> --场景uid <阶段0给的> [--配色 /tmp/配色.json]
```

配色 JSON 是 `{"旧色字面量": "新色字面量"}`。**精度必须照抄文件里的实际写法** ——
场景里写 `Color(0.043, 0.129, 0.235, 1)` 三位小数，你用六位 `0.043137` 去匹配会
静默失败。脚本会为每条规则单独报命中次数，0 次的会被标红并让整个脚本失败。

派生脚本只做机械替换。**几何值和字色不会自动跟着变**，接着要人工做：

- `texture_margin` / `content_margin` 按本套骨架调（斜切量、角标臂长要落在保护区内）
- 亮底套：字色按具名 key 逐项改墨色（拓荒纪事改了 11 项），`modulate_color` 提亮值
  从 1.12~1.2 压回 1。**不要全局替换色值** ——同一个骨白在深色按钮上是对的
- 场景根节点改名、占位文字（`placeholder_text`、`popup/item_N/text`）改成本套语境

改完必须跑 import，否则 uid 不进 `.godot/uid_cache.bin`：
```bash
"$GODOT" --headless --path . --import
```

**Godot 编辑器开着时不要改 `.tscn`** ——会被整文件 resave 污染（sub_resource 按字母序
重排、文件头注释被剥离），diff 从 4 行涨到 500 行。提交前查 diff 行数。

**闸门**：
```bash
python3 tools/验收/检查主题.py --套 <套别名>
```
七项断言。其中两项是别处查不出来的：`texture_margin` 的 T+B 必须 < 贴图高（相等就
中心行 0px，九图完全退化，十一到十四套全栽过）；交叉引用 uid 必须与目标文件实际
uid 一致（uid 失效时 Godot 静默回退 path 照常加载，断链能潜伏好几套）。

## 阶段 3 测试台四层验收

```bash
bash tools/验收/全量验收.sh <套别名>
SKIP_SHOT=1 bash tools/验收/全量验收.sh <套别名>    # 沿用现有截图，省 30 秒
```

四层串联，前一层不过不进下一层：素材 → 静态 → 几何（探针实测）→ 截图（真渲染）。

出问题先看 `硬约束清单.md` 对应条目，多数坑那里都记了判据和修法。两条最反直觉的：

- **截图不能加 `--headless`** ——它强制 dummy 驱动盖掉 `--rendering-driver opengl3`，
  存出来是纯色图，而验收还会「通过」。报错特征：`rendering/dummy/storage` + 窗口高 64
- **HBoxContainer 会把子节点纵向拉到最高兄弟的高度**，判定基准必须是
  `get_combined_minimum_size().y` 而不是 `custom_minimum_size.y`。修法：
  给该节点 `size_flags_vertical = 4`

**新套跑通后，务必拿其它套也跑一遍。** 脚本只在新套上写，交叉验证四套时四套全报红，
且全是已交付主题里的真 bug——这是整个验收体系最大的一次收获。

**闸门**：四层全过。色相占优那条是 [半自动]，不符合定位时先判断是素材问题还是配置
写错，**不要把断言调松让它变绿**。

## 阶段 4 注入游戏项目

> **完整闭环已走通两次。** 下面标 ✅ 的是实测出来的，标「设计」的仍未验证。
>
> **第一次**：游戏项目「卡牌对战」从原生 UI（26 处场景 inline StyleBox +
> 11 处代码 override）注入义体裂界（深色皮 → 深色皮），改完五层测试全过。
> 抓到三个静态扫描看不见的问题：汉字 tofu（4.4）、`content_margin` 缺省顶大控件
> （4.3）、主题缺类型（4.3）。
>
> **第二次**：游戏项目「荒野生存」从原生 UI（11 处场景 + 1 处代码）注入
> 拓荒纪事，**深色皮 → 浅色皮**，硬拦路项 12 → 0，测试从六步扩到七步 192 项断言。
> 又抓到三个第一次没暴露的：**浅底撞字色**（4.5，牵连 12 处文字，前五层全放过）、
> **素材库现成件不等于能用**（4.3）、**像素法测不了对比度**（4.5）。
>
> 两次的差别值得留意：**换同色系皮和跨色系皮不是一个难度**。第一次深→深，
> 字色几乎没动；第二次深→浅，面板里每一段文字都要重挑颜色。
> 接活前先看目标皮和项目原来的明暗关系，那决定了工作量在哪。

### 4.1 体检（只读，先看清再动手）

```bash
python3 tools/脚手架/扫描游戏.py --项目 <游戏项目路径> --套 <套别名>
python3 tools/脚手架/扫描游戏.py --项目 <游戏项目路径> --套 <套别名> --详细
```

报六节。硬拦路项是 [1]、[5] 的 StyleBox 部分、[6]：

- **[1] `.tscn` 里的 inline StyleBox override —— 换肤失效的头号原因。** 节点自带的
  StyleBox 完全盖掉 theme 的同名项，theme 换了界面纹丝不动，**且不报任何错**。必须先清
- **[2] `.tscn` 里的其它 override（字色/字号/常量）。不一定要删** ——布局常量和字号
  层级是版面不是皮肤，局部强调色往往是有意的。但**字色那批是雷区**：换肤后可能和
  新底色撞，浅底白字直接看不见。✅ 第二次注入这条牵连 12 处文字。
  **它不是"逐项人眼过一遍"能可靠覆盖的，需要一层对比度断言**——做法见 4.5。
  注意这一节报的数字是**下限**：`[color=#xxxxxx]` 写在 BBCode 文本里，扫不到
- [3] theme 引用点：脚本自己读 `project.godot` 的 `gui/theme/custom`，全局和逐节点都会报。
  ✅ 这条是那次注入现场修的 —— 原来只解析 `.tscn`，于是换肤做完、theme 已经挂上了，
  这一节还在报「整个项目没有节点显式设 theme」。**结论与事实相反，比不报更糟**
- [4] 贴图直引：换 theme 时这些引用不会跟着走，要逐个改到新套目录
- **[5] 代码里的 `add_theme_*_override`。** 效果和 [1] 完全一样，但改场景文件不管用，
  必须改代码，所以更难找。计数按行算，一行循环造四个态只报 1 处，数字是下限
- [6] TextureRect 尺寸对表：不等比的要么改节点尺寸要么重出素材。九图不查（它被拉伸
  是正常用法，风险在 `texture_margin`，那条由阶段 2 负责）

「静态读不到尺寸」那部分靠 anchors/Container 算，**不能当成通过** ——要等注入后实测。

### 4.2 注入前先备份

游戏项目是用户的正式代码。**动手前确认它在 git 里且工作区干净**，不干净就先问用户。
没有版本控制就不要改，先让用户建仓或手工备份。

### 4.3 注入

1. 拷素材目录到游戏项目，跑 `--import`
2. 拷 `.tres` 主题
3. 按体检清单清 [1] 和 [5] 的 StyleBox、改 [4]、修 [6]
4. 把 theme 挂上（节点 `theme` 属性，或 `project.godot` 的 `gui/theme/custom`）

✅ **拷素材时把 `.svg.import` 一起拷，uid 一条都不会失效** —— 这是那次实测的结论，
比原先写的"重对 uid"省一整步。`.import` 里存的是 uid 和 `res://` 路径，只要两边
路径同为 `res://UI/<套名>/...`，48 条 `ext_resource` 原样有效：

```bash
cp -R <UI组件>/UI/<套名> <游戏项目>/UI/     # 连 .import 一起
cp <UI组件>/theme/<主题>.tres <游戏项目>/theme/
```

拷完仍要跑 `--import`（生成 `.godot/imported/` 下的实际资源），但不用改 `.tres`。
**验证方式不是看 import 有没有报错**（grep 过滤后什么都不剩很容易误判成成功），
而是加载主题后逐个查 `StyleBoxTexture.texture != null`：

```gdscript
var t := load("res://theme/<主题>.tres") as Theme
for ty in t.get_type_list():
    for k in t.get_stylebox_list(ty):
        var sb := t.get_stylebox(k, ty)
        if sb is StyleBoxTexture and (sb as StyleBoxTexture).texture == null:
            print("空贴图: %s/%s" % [ty, k])
```

若路径不同（改了目录名），才需要按目标项目的 `.svg.import` 重对 uid —— 不重对会报
一片 `invalid UID: ... - using text path instead` 然后 `No loader found for resource`，
`tools/脚手架/派生主题.py` 干的就是这件事。

✅ **主题几乎一定缺游戏要用的类型，先列清单再改场景。** 组件库覆盖的是通用控件，
游戏总有它没有的。两次注入各补了 8~9 类，重合度很高：`RichTextLabel`（组件库里
没这个控件）、三色 `ProgressBar` 变体（血条/数值条）、按钮牌面变体、`LabelWin/Lose`、
`HScrollBar`（不补就是 Godot 默认灰条，贴在任何一套皮上都突兀）。先跑一遍看清有什么：

```gdscript
for ty in t.get_type_list():
    print("%s 变体base=%s stylebox=%s" % [ty, t.get_type_variation_base(ty),
        str(t.get_stylebox_list(ty))])
```

✅ **补变体优先另建，不要改组件库自带的类型。** 第二次注入要给「过夜按钮」深色字，
`ButtonGold` 的近白字对金底只有 2.07:1。直接改 `ButtonGold` 等于替源库做决定，
而且下次从源库重拷主题时改动会**静默丢掉**。建个 `base_type = &"ButtonGold"` 的
新变体只覆字色，金底原样继承。

✅ **"素材库有现成件"不等于"那件能用"，得量过像素才算。** 第二次注入要三色数值条，
素材库正好有 `线性进度条填充绿.svg` / `填充金.svg`，于是直接拿来用、还在注释里写了
"不必重出图"。**实测三条渲染出来逐像素相同** —— 那三个 SVG 只在一处不同：一条
`opacity="0.16"` 的宽笔画的颜色，其余深棕和浅色描边完全一致。带颜色的成分只占
16% 不透明度，像素上区分不出来。

改用 `modulate_color` 乘在同一张贴图上，三条才真的分开（还保住了笔触纹理）。
**教训是"文件名对得上"不构成验证**，得渲染出来量：

```python
# 量两条的填充段均色，相同就是没生效
# ★只量三条都确实填到的那一段，否则量进空槽 —— 空槽三条共用同一张贴图，
#   量到的当然一样，会得出"三色没区分"的错结论（第一次就是这么误判的）
```

✅ **`StyleBoxTexture` 的 `content_margin` 必须显式写。** 缺省会跟随 `texture_margin`，
于是 `texture_margin = 26` 就意味着控件最小尺寸被顶大 52px。那次注入的花费角标
代码里给的是 44×44 框，实测量出 65×77，直接压到牌名上糊成一团。
**最小尺寸是 min，anchor offset 压不住它**，只能从 `content_margin` 这头治。

这和「九图退化」是两条不同的判据，都要查：

| 判据 | 比什么 | 症状 |
|---|---|---|
| 九图退化 | `texture_margin` 总和 vs **贴图**尺寸 | 四角重叠，装饰件糊成一团 |
| 控件顶大 | `content_margin` 总和 vs **控件**期望尺寸 | 控件被撑大，压到邻居 |

前者阶段 2 的 `检查主题.py [2]` 查；后者只能注入后实测，`112×112` 的贴图切 26 边距
完全合法，贴到 44×44 的角标上就出事。

✅ **哪些 override 该留，判据是「换一套皮这个值该不该跟着变」。** 那次注入：
- 胜利绿/失败红 → **进 theme**（每套主题的绿红都不同）
- 卡牌类型主色（红攻/蓝防/绿疗/金抽）→ **留在代码里**，那是玩家要辨认的游戏语义，
  换皮不该抹掉。它会继续出现在体检 [5] 里，是有意保留不是漏清
- 布局常量（margin/separation）、字号层级（标题 60 > 副标题 24）→ **留**，那是版面不是皮肤

### 4.4 注入后实测

✅ **最重要的一条：肉眼看图。** 那次注入五层测试全绿的同时，图上「敌方城堡」是四个
带 hex 码点的方框。**没有任何自动断言抓到它** —— 方框也是像素、控件尺寸也没变、
数据同步也对。静态扫描、几何探针、像素分布校验全都判它通过。

出图后逐张 Read，看不清就裁出来放大（按探针给的坐标裁，别凭感觉估位置 ——
我第一次裁偏了 300px，把面板底纹当成了 tofu，得出了错的结论）。

✅ **汉字 tofu：主题必须有 `default_font`。** 症状极具迷惑性 —— 同一屏「我方城堡」
正常、「敌方城堡」是方框，两个 Label 的字号和变体完全一样。

根因：`default_font` 为 null 时 Label 拿到 Godot 内建 Open Sans（只有拉丁字形），
汉字全靠 OS 回退，而**回退是按整串首字挑字体的**：「我」挑到真 CJK 字体，「敌」挑到
macOS 的 Last Resort —— 一个对任何码点都"有字形"的兜底字体，画出来就是 hex 方框。

```gdscript
[sub_resource type="SystemFont" id="Font_cjk"]
font_names = PackedStringArray("Heiti SC", "Hiragino Sans GB", "Songti SC", "STHeiti", "Arial Unicode MS")
allow_system_fallback = true
```

字体列表是逐个渲染实测筛的。**PingFang SC 落选**：它自己缺「敌」，advance 混着 24 和 26。

**判 tofu 只能看 `font_rid`，不能看 glyph index。** Last Resort 对每个码点都返回非 0
index —— 我就是这么误判的，报了「0 处 tofu」而图上明明有四个方框。advance 差异
（方框 24 / 真字形 26）是旁证，但依赖具体字体，不如 `font_rid` 硬。

✅ **补一层字形探针把这个洞焊死**，`卡牌对战/tests/测试字形.gd` 可照抄（**注意**：这个文件在
`卡牌对战` 游戏项目里，不在本套件库——若目标项目没有，就照下面要点现写一个）。要点：
- 按控件取字体（`c.get_theme_font("font")`），不是统一用 `theme.default_font` ——
  变体可以各自覆盖字体，换肤时正是变体最容易漏配
- 断言「查到的文字段数 ≥ N」。**探针空跑必须报红**：初版用 lambda 计数器，
  GDScript 按值捕获改不到外层变量，于是报「查了 0 段文字」却「全部通过」，
  假绿比不加这层更危险
- 写完要双向验证：摘掉 `default_font` 必须报红且退出码为 1。
  注意 `cmd | grep` 的 `$?` 取的是 grep 的码，得先重定向再取

**先跑游戏项目自己的测试。** 换肤只该改样式，功能一项都不该变——目标项目若有测试
套件，那是最强的回归闸门。`卡牌对战` 五层（逻辑/界面/几何/字形/版面）、
`荒野生存` 七步（多了 4.5 的对比度层，和拆开的截图+版面）：

```bash
cd <游戏项目> && bash tests/全部测试.sh
```

再拿探针实测几何，这是唯一能覆盖「静态读不到尺寸」那批的手段：
```bash
"$GODOT" --headless --path <游戏项目> \
    -s <探针脚本> -- --套 <套别名>
```
`tools/验收/探针.gd` 假定场景结构是 `Scroll/VBox/Margin/Inner`，游戏场景不是这个结构，
要按目标场景改 [3] 那段，或只用 [1][2] 两段。

**headless 下量几何必须用 `SubViewport`**，不能直接挂 `get_root()`：主窗口锁死在
64×64，`get_root().size` 赋值过一帧就被打回，`--resolution` 也无效。于是所有容器按
64×64 排版，量出来的数字全是废的，还会把「元素未居中」这类假问题报成 bug。
`卡牌对战/tests/测试几何.gd` 是可照抄的写法（在 `卡牌对战` 项目里，不在本套件库）。

✅ **先在换肤前的分支上拿基线，再判「这是不是换肤引入的」。** 那次 tofu 我一开始以为
是换肤造成的，实际换肤前就有。用 worktree 出基线图，按各自实测坐标量同一处：

```bash
git worktree add /tmp/基线 main && cd /tmp/基线
<godot> --headless --path . --import && <godot> --path . -s tests/截图.gd
# 量完 git worktree remove /tmp/基线 --force
```

两处坐标**不能共用** —— 换肤后面板内边距变了、标签 y 不一样，用错坐标会量出「无墨」
然后误判成"基线根本没渲染"。同理阈值也要按亮度判，不能要求三通道都亮：
基线标题是红字（g/b 才 102），「三通道 >140」会把它判成没有内容。

✅ **基线也用来判警告是不是自己引入的。** 第二次注入加载主题时冒出两条
`invalid UID`，在源库跑同一句 `load()` 是 0 条 —— 于是确定是注入引入的，
不能当"本来就有"放过。根因是 `.godot/uid_cache.bin` 没收录（`.import` 里的 uid
和主题、源库三处其实一致），删掉缓存重跑 `--import` 就清了。
**别看到警告就改文件**，先确认它指的是不是真问题。

**闸门**：换肤前后**节点树与功能必须不变**。只换皮，不改结构。目标项目的测试全过
（跨明暗换皮时还要过 4.5 的对比度层）。

### 4.5 跨明暗换皮：字色对比度（✅ 第二次注入新增）

**深底项目换浅底皮（或反过来）时，面板里每一段文字都要重挑颜色。**
这是第二次注入最大的收获，也是第一次（深→深）完全没暴露的一整类问题。

症状：拓荒纪事的面板是浅米底 `rgb(227,208,170)`，而它自己的 Label 字色是近白
`rgb(246,236,210)` —— **对比 1.29:1，字实际上看不见**，全靠一圈深色描边才勉强
认出形状。牵连 12 处：8 个行动按钮、过夜按钮、结局标题、日志和说明里的 BBCode
语义色。**注意连主题自带的配色也会撞** —— 组件库的 Label 字色是按它自己的深色
预览底选的，未必配它自己的浅色面板。

★**前五层测试一个都抓不到**，这是它危险的地方：

| 层 | 为什么放过 |
|---|---|
| 逻辑 | 规则没变 |
| 界面 | 文本内容对，字色不管 |
| 几何 | 尺寸没变 |
| 字形 | 字形画得出（tofu 探针只管"有没有字形"，不管"看不看得见"） |
| 截图 | 糊掉的字仍是非背景像素，占比/空白/跨度全正常 |

所以要**单独补一层**。`荒野生存/tests/测试对比度.gd` 可照抄（**注意**：这个文件在
`荒野生存` 游戏项目里，不在本套件库——若目标项目没有，就照下面要点现写一个）。要点：

- 判据用 WCAG 相对亮度公式，阈值 **4.5:1**（AA 正文），大字号（≥24px）按 3:1。
  **这是外部标准不是自己挑的数**，所以不存在"调松让它变绿"的空间
- 字色取 `c.get_theme_color("font_color")`（RichTextLabel 是 `default_color`）——
  控件**实际解析到的**值，变体覆盖也算进去
- 底色**往上找最近的祖先面板**，取它 StyleBox 贴图的**中心像素**（边缘是描边和
  圆角，中心才是文字真正坐上去的那片），再乘 `modulate_color`。
  Button 的文字底是它自己的 `normal` StyleBox，不是祖先面板
- `[color=#xxxxxx]` 写在 BBCode 文本里，`get_theme_color` 取不到，**要单独对表**。
  漏了就漏掉一整类（日志的报警色、说明的分类色都在这里）
- 同样要断言「查到的段数 ≥ N」，防探针空跑假绿

★★**对比度不能用像素法测。** 这条踩得很深，值得完整记下来：

第一版写在截图层，判据是「量标签矩形里出现最多的颜色当底、第二多里最亮的当字」。
浅底文字带一圈深描边，**描边像素比字芯多** —— 于是描边色被当成"底"、字芯被当成
"字"，量出 **9.71:1 的漂亮数字**，而真实情况是 1.29:1。

怎么发现的：手动把血标字色改成接近底色的深棕（本该报红），**三个数字一字未变**。

> **改坏输入却不动的断言，就是没在量它以为在量的东西。**

描边、抗锯齿、九图纹理都会污染「哪个像素是字、哪个是底」的判断，像素法治不了。
改在 Godot 侧直查 —— 没有歧义。

**闸门**：全部文字 ≥ 4.5:1（大字 3:1）。写完先手动破坏一次，确认它真报红。

## 别做的事

- 不要为了让验收变绿而调松断言。色相占优那条至今是红灯，价值恰恰在于它没被调松
- 不要把 [人工] 条目改写成 [自动] 断言凑数。判不了就是判不了，假装能判比不查更糟
- 不要跳过阶段 1 的契约直接派生。素材尺寸错了要一路等到截图层才以「控件变形」暴露
- **不要只看断言全绿就交付。** 五层全过的同时界面上可以有四个 hex 方框。出图后逐张看
- **不要用 glyph index 判 tofu**，也不要拿"脚本没报错"当验证。查 `font_rid`、查
  `texture != null`，用能证伪的判据
- **不要拿"断言绿了"当"断言在工作"。** 每写一条新判据，先手动把输入改坏成它本该
  报红的样子，看数字动不动。**改坏输入却一字不变的断言，就是没在量它以为在量的
  东西** —— 对比度那条量出 9.71:1 而真实是 1.29:1，就是这么抓出来的
- **不要因为"素材库有现成件"就断定那件能用。** 拿它量过像素才算成立。三色进度条
  那三支 SVG 只有一条 16% 不透明度的笔画换了颜色，渲染出来逐像素相同
- 不要 `git commit`，除非用户明说要存 git。`git push` 一律先问
